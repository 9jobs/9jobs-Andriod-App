# Client ID implementation — local review and activation runbook

Status: local implementation only. No live spreadsheet, database, trigger,
authentication configuration, or deployment has been changed by this work.
Production activation requires separate approval and fresh verified backups.

## Behavior and identity

`apps-script/ClientSync.gs` is a **replacement** for the audited `Code.gs`, not
an additional file to install alongside its clearing functions. Keep an exported
copy of the old source for recovery, but never re-enable its destructive refresh.

The script creates `Client_Registry` in the exact approved Duplicate only. Its
seven columns are Client_ID, Source_Spreadsheet_ID, Source_Sheet_ID,
Candidate_Name, Created_At, Last_Seen_At, Account_Mapping_Status. UUID v4 IDs have
the `9JOBS-CL-` prefix and are allocated under the shared script lock. IDs are
never generated by the backend, stored in Master, or inserted into All_Jobs.
The database holds a private mirror and the authorized account mapping.

Identity uses the Master spreadsheet ID and numeric source sheet ID. Names do
not establish ownership. A rename retains the ID; same-name source sheets have
separate IDs. Copied/recreated sheets have new source IDs and must not be
silently merged with a former client. If two source sheets represent one actual
person, stop for operator review rather than guessing or granting two accounts.

The registry's mapping-status cell is an initial `pending` value. Actual live
mapping/revocation status is authoritative in the private backend; no write-back
through the Viewer service account is attempted.

## Non-destructive synchronization and timeout recovery

Legacy All_Jobs, Candidate_Index, candidate tabs, formulas and hidden markers are
retained untouched. All_Jobs keeps its twelve columns. The new authoritative
feed is a committed generation in new protocol tabs, rather than clearing and
rebuilding those legacy tabs. Existing legacy tabs remain a historical reference.

The script creates only minimally sized new tabs, using the authorized Apps
Script account and the Sheets addSheet API. Source rows are written as literal
rich text, including formula-like strings. No source profile/password rows are
exported. No service account write privileges are needed.

New tabs are Client_Registry, Client_Registry_Review, Client_Sync_Manifest,
Client_Sync_Log, Client_Sync_Checkpoints, Client_View_Manifest, immutable
`_9JOBS_DATA_g_<uuid>_<part>` parts, and stable `Client_View_<source_sheet_id>`
candidate views. Ownership of newly created tabs is recorded in script
properties; colliding manually created tabs are rejected for review.

Each invocation works for at most approximately 180 seconds, checking its budget
between bounded 250-source-row chunks. Discovery, extraction, verification and
candidate views have resumable checkpoints. A single upstream service call can
still be slow; a hard platform termination preserves the prior checkpoints and
committed data. This is recoverability, not a claim that Google cannot time out.

Every part is checksum-verified, and source windows are read again before a
COMPLETED log record is appended. Consumers ignore incomplete and ABORTED
generations. Retries verify an existing part instead of clearing or replacing it.
Unchanged parts are reused. Changing sources abort the incomplete generation
without deleting it; the next scheduled run starts fresh with existing IDs.
Backend transactions reject decreasing record counts, identity reassignment,
older generations, missing registry entries and invalid provenance, preserving
the current head and historical records.

`hourlySyncStaged` retains its two-hour entry point. One-shot
`syncCandidateViewsAuto` continuations resume pending work and project committed
parts into the **new stable-ID candidate views**. Their append journal prevents
repeat insertion. Changed source parts append historical versions to these
views; the backend's current generation contains only current source records.
Existing name-based candidate tabs and their J1/J2 markers are never overwritten.

No automatic deletion/retention cleanup exists. A 9.5-million-cell guard stops
growth safely. If capacity is reached, review an additional-workbook migration
that preserves all existing data; do not delete old tabs to free capacity.

## Authentication and existing Admin/Android integration

Token exchange verifies the Clerk signature, pinned issuer/JWKS, algorithm,
expiry, authorized origin and subject, then checks the actual session ID,
user ID, active status and expiry with Clerk's Backend API. The primary email
must be verified in a server-side user lookup. Request names, emails, roles,
user IDs and Client IDs cannot choose ownership.

The existing token response and login/register screens remain. Mobile and Admin
send their existing Clerk bearer session to the existing exchange endpoint.
New backend JWTs are marked, issuer/audience-bound, and require a configured
strong secret. Legacy/demo JWTs are rejected; existing sessions need a fresh
exchange. Offline demo login remains local and cannot mint backend identity.
Password-admin login remains available through server-only ADMIN_LOGIN_EMAIL
and ADMIN_LOGIN_PASSWORD configuration, but cannot read private sheet data.
Private sheet endpoints require an active Clerk session, including for admins.

Verified account persistence updates only identity fields, preserving existing
roles, suspension state, subscriptions and other profile data. Email conflicts
stop for review rather than merging accounts. `backfill-clerk-accounts.cjs`
can mirror existing Clerk accounts after approval, including unverified accounts
as pending_verification. It never maps them to candidate data. Profiles returned
by the existing database and personal-info APIs use the authenticated account
directory's names/emails, preserving the existing Admin UI.

An operator-approved exact Clerk subject and Client ID are linked using
`approve-client-account.cjs`. Both account and client must exist; the account
must have completed verified login. Constraints prevent duplicate ownership and
silent transfers/re-enabling of revoked mappings. No public claim API exists.
Legacy candidate-label/email approvals remain stored but grant no access through
the new data path. The legacy importer is disabled unless explicitly opted in;
it cannot publish name-only data for private clients.

No UI fields or badges were added. Admin authentication now forwards the Clerk
bearer session, validates password login on the server, and removes the bundled
default password and false-success/direct-database fallback. Expired password
sessions require re-entry in the existing form. Mobile SessionProvider changes
register/clear the token getter; JSX, screens, navigation and styles are unchanged.

## Production activation — gated sequence

Do not execute these steps as part of local Phase 3.

1. Obtain the **separate daily backup project's actual URL**. The URL supplied
   twice points to the Master Sync project, which currently shows only the
   two-hour trigger. Verify the backup code, source ID, daily schedule, latest
   successful execution and backup artifact read-only. Do not alter that system.
2. After approval for production preparation, pause only the failing sync as
   described above. Create fresh timestamped recovery copies of the Duplicate
   and source/manifest/properties, and a database logical backup. The Master
   must never be written to; use the separate existing Master backup for source
   restoration evidence. Restrict all backup access.
3. Restore the spreadsheet backup to an isolated copy and the database dump
   to a new isolated database. Compare all rows, formulas, tab IDs/metadata,
   markers and table checksums/counts. The local synthetic restore test is
   evidence for the procedure, not a substitute for this production restore.
4. Review the source sheet inventory. Run the read-only dry run on isolated
   copies first. Configure CLIENT_SOURCE_SHEET_IDS as a JSON array of reviewed
   numeric source IDs (strings). Configure CLIENT_TEMPLATE_SIGNATURES only
   after confirming the structural signature is exclusive to genuine candidate
   templates, including their zero-job layout. Unrecognized sheets go to the
   review tab and receive no ID. Never approve by name alone.
5. Test the exact patch on an isolated Master/Duplicate pair using a reviewed
   copy of CLIENT_SYNC.master/duplicate constants. Never use production IDs
   while running isolated spreadsheet tests. Test Apps Script consent, timing,
   rich text round trips and capacity on Google-hosted copies.
6. Following **separate activation approval**, replace the live Code.gs with
   the reviewed replacement. Keep CLIENT_SYNC_ENABLED=false. Do not retain
   duplicate old function definitions. Preserve the project's timezone and
   other settings. The existing script owner authorizes spreadsheet access,
   trigger management and external requests. Required scopes are
   https://www.googleapis.com/auth/spreadsheets,
   https://www.googleapis.com/auth/script.scriptapp, and
   https://www.googleapis.com/auth/script.external_request.
   Verify Sheets API availability in the Apps Script-associated Cloud project;
   the service account's Cloud project is not necessarily the same project.
   No Drive scope or change to service-account Viewer access is required.
7. Apply migrations/20261102_client_registry.sql through the reviewed migration
   process to the explicitly approved database. It creates additive private
   tables; it does not modify/drop existing profiles or application tables.
   Check existing definitions for conflicts before applying: IF NOT EXISTS
   intentionally does not silently repair incompatible existing tables.
8. Configure server secrets through the existing secret manager: DATABASE_URL,
   JWT_SECRET (at least 32 random characters), CLERK_ISSUER, CLERK_SECRET_KEY,
   CLERK_AUTHORIZED_PARTIES and SHEET_ADMIN_USER_IDS (verified admin subjects).
   If preserving password-admin login, configure ADMIN_LOGIN_EMAIL and a new
   private ADMIN_LOGIN_PASSWORD distinct from the former bundled default. Do not paste secrets into scripts, chat,
   Sheets, source files, logs or frontend builds.
9. Deploy the reviewed backend and Admin/mobile authentication transport updates
   through the existing release process. Existing tokens need reauthentication;
   never restore acceptance of forged/demo identity to avoid that transition.
   Keep the existing feature flags off until the production smoke test is ready.
10. Set CLIENT_SYNC_ENABLED=true and run one approved initial generation. Verify
    Client_Registry uniqueness against the reviewed source-ID inventory, exact
    35,122-or-higher approved record baseline, completion checksum, candidate
    views and original tabs/formulas/markers. If the source legitimately has
    fewer current records, stop for review rather than bypassing the count guard.
11. On the approved worker host, explicitly supply DATABASE_URL and
    CLIENT_ID_DATABASE_HOST (its exact hostname). The operator tools reject
    missing/mismatched targets rather than falling back to repository defaults.
    Also supply GOOGLE_DUPLICATE_SPREADSHEET_ID,
    GOOGLE_SHEETS_SERVICE_ACCOUNT_FILE (secure external path),
    CLIENT_ID_EXPORT_DIRECTORY (private, outside any web root), and
    CLIENT_ID_SYNC_ENABLED=true. Run from backend:

    `node scripts/sync-client-generation.cjs`

    This uses Viewer-only Google reads, writes an immutable private export, and
    imports transactionally. It installs no schema or scheduler. A successful
    pointer avoids rereading unchanged data; if intentionally reinitializing a
    database, use a fresh export directory so a stale local pointer cannot skip
    the first import. Keep one worker configuration per target database.
12. For existing accounts, set CLIENT_ID_ACCOUNT_BACKFILL_ENABLED=true only for
    an approved operator run of `node scripts/backfill-clerk-accounts.cjs`.
    Review identity/email conflicts without overwriting accounts. Verified
    clients complete an ordinary Clerk login, which populates verified_accounts.
13. Prepare a private approval JSON file containing action=link, exact userId,
    exact clientId and approvedBy after independently checking the client
    relationship. Set CLIENT_ID_MAPPING_APPROVAL_FILE to its path and
    CLIENT_ID_MAPPING_ENABLED=true, then run
    `node scripts/approve-client-account.cjs`. There is no name-only backfill.
14. Enable existing backend/Admin/mobile sheet-integration flags. Test two real
    approved accounts, an unlinked account, revoked mapping/session, direct
    request tampering and the existing Admin listing/Android screens. Test with
    actual Clerk credentials entered by their owners; fixtures do not replace it.
15. Restore the single two-hour trigger and its separate one-shot continuation
    workflow. Schedule the approved Node worker on the existing trusted worker
    host (for example every five minutes to check for a new COMPLETED log).
    No production scheduler was installed by this change. Monitor generation
    completion, counts, retries, capacity and errors without logging source rows.

For rollback, pause the new sync/worker and disable integration flags. Keep all
registry IDs, versioned tabs and database history. Restore backups to a **new**
isolated destination for review; never truncate production or resume the old
clearing functions. Existing app accounts and unrelated data remain intact.

## New backend/API entry points

Existing POST /api/auth/token and GET /api/mobile/sheet-records[/version] are
retained with stronger verification and permanent ownership joins.
GET /api/admin/client-accounts is an admin-only backend directory endpoint;
no new UI consumes or displays Client ID fields. Existing Admin profiles and
personal-info results are hydrated with authenticated account names/emails.

Important new functions: parseRegistry, mirrorRegistry, approveClientAccount,
validateClientExport, lookupVerifiedAccount, persistVerifiedAccount,
hydrateVerifiedProfiles, backfillClerkAccounts, readClientGeneration,
dryRunClientRegistry, clientSyncStep_, clientViewStep_ and
abandonIncompleteClientGeneration. None performs an automatic live migration.
